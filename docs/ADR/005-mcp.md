# ADR-005: MCP como tools boundary

- **Fecha:** 
- **Estado:** Aceptada

## Contexto

El agente de investigación de incidentes necesita interactuar con diferentes sistemas externos para obtener la información necesaria durante una investigación.

Entre las integraciones previstas se encuentran:

- Logs.
- Métricas.
- Traces.
- Git y repositorios de código.
- Deployments y CI/CD.
- Sistemas de gestión de incidentes.

Estas capacidades deben estar disponibles para el razonamiento agentic, pero no queremos acoplar directamente el agente con la implementación de cada integración.

Se identifican dos tipos de herramientas:

1. **Capacidades propias del dominio de investigación**, como la construcción de hipótesis, correlación de evidencia o generación de timelines.

2. **Integraciones con sistemas externos**, como consultar logs, métricas, Git o Kubernetes.

Estas dos categorías tienen diferentes responsabilidades y necesidades de evolución.

La arquitectura buscada es:

```
                    Investigation Agent
                            │
             ┌──────────────┴──────────────┐
             │                             │
       Domain Tools                  MCP Client
             │                             │
             │                             ▼
             │                       MCP Server
             │                             │
             │              ┌──────────────┼──────────────┐
             │              ▼              ▼              ▼
             │            Logs          Metrics           Git
             │
             ▼
       Domain Logic
```

El objetivo es establecer una frontera clara entre el razonamiento del agente y las integraciones con infraestructura externa.

## Alternativas consideradas

### 1. Tools integradas directamente en el agente

Ventajas:

- Menor complejidad arquitectónica.
- Menor latencia entre el agente y las herramientas.
- Implementación y debugging más sencillos.
- Los contratos de las herramientas pueden utilizar directamente los tipos internos de la aplicación.
- No requiere desplegar un componente adicional.
- Adecuado para una primera implementación con pocas integraciones.

Desventajas:

- Acopla el agente directamente con las integraciones externas.
- Las herramientas son más difíciles de reutilizar desde otros agentes o aplicaciones.
- El runtime del agente puede acumular lógica de integración con múltiples sistemas.
- Los cambios en una integración pueden requerir modificar y desplegar nuevamente el agente.
- Las credenciales y clientes de sistemas externos quedan más próximos al runtime del agente.
- La separación entre razonamiento e infraestructura se vuelve menos clara.

### 2. MCP como boundary de tools

Ventajas:

- Define una frontera clara entre el agente y las integraciones externas.
- Permite reutilizar las mismas herramientas desde diferentes agentes o clientes.
- Permite evolucionar las implementaciones de infraestructura independientemente del agente.
- Facilita centralizar autenticación y acceso a sistemas externos.
- Permite encapsular clientes específicos de infraestructura dentro del MCP server.
- Facilita incorporar nuevas integraciones sin introducir directamente su implementación en el runtime del agente.
- Establece contratos explícitos entre el agente y las herramientas.
- Permite evolucionar posteriormente hacia múltiples agentes consumidores de las mismas capacidades.

Desventajas:

- Añade un componente adicional a la arquitectura.
- Introduce potencialmente mayor latencia en las llamadas a herramientas.
- El debugging y la observabilidad son más complejos al existir una frontera de red/proceso adicional.
- Requiere gestionar versionado y compatibilidad de los contratos de las herramientas.
- Añade complejidad operacional para un MVP pequeño.
- MCP no elimina la necesidad de diseñar correctamente permisos, validación, timeouts y límites de ejecución.

## Decisión

Adoptaremos MCP como boundary para las herramientas que representan integraciones con sistemas externos.

Las herramientas propias del dominio de investigación permanecerán integradas directamente en el agente cuando no exista una necesidad de exponerlas como servicios independientes.

La separación será:

```
┌─────────────────────────────────────────┐
│           Investigation Agent           │
│                                         │
│  Domain capabilities                    │
│  ├── create_hypothesis()                │
│  ├── evaluate_evidence()                │
│  ├── correlate_events()                 │
│  └── build_timeline()                   │
│                                         │
│              MCP Client                 │
└────────────────────┬────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────┐
│              MCP Server                 │
│                                         │
│  Infrastructure capabilities            │
│  ├── query_logs()                       │
│  ├── query_metrics()                    │
│  ├── query_traces()                     │
│  ├── get_deployments()                  │
│  ├── get_git_changes()                  │
│  └── get_kubernetes_state()             │
└────────────────────┬────────────────────┘
                     │
                     ▼
             External Systems
```

El agente será responsable del razonamiento y planificación de la investigación, mientras que las herramientas MCP serán responsables de proporcionar acceso controlado y estructurado a sistemas externos.

Las herramientas deberán tener contratos explícitos de entrada y salida y deberán aplicar validación, autorización y límites de ejecución apropiados.

MCP no se establece como requisito para todas las herramientas. Se utilizará cuando la herramienta represente una integración externa que se beneficie de desacoplamiento, reutilización o evolución independiente.

## Consecuencias

### Positivas
- Separa el razonamiento del agente de las integraciones de infraestructura.
- Reduce el acoplamiento entre el agente y los sistemas externos.
- Las herramientas pueden reutilizarse potencialmente por múltiples agenteso consumidores.
- Permite evolucionar las integraciones sin modificar necesariamente elrazonamiento del agente.
- Facilita centralizar controles de acceso y credenciales en el boundary deherramientas.
- Permite mantener las herramientas como interfaces deterministas yestructuradas.
- Facilita incorporar nuevas fuentes de información para la investigación.
- La arquitectura mantiene una distinción clara entre: `Agentic reasoning`, `Tool contract`, `External system`.

### Negativas
- Se introduce un MCP server como componente adicional.
- Aumenta la complejidad de despliegue y operación.
- Las llamadas a herramientas pueden tener mayor latencia.
- El debugging requiere observar tanto el agente como el MCP server.
- Los contratos MCP requieren una estrategia de versionado y compatibilidad.
- Para integraciones pequeñas o exclusivamente internas, MCP puede introducir complejidad innecesaria.

### Riesgos
- **Diseño excesivamente genérico de las tools:** herramientas demasiado
genéricas pueden dar al agente capacidades difíciles de controlar o
utilizar correctamente.

- **Exceso de autonomía:** el agente podría ejecutar herramientas de manera inesperada o realizar demasiadas consultas. Se deberán establecer límites como max_steps, max_tool_calls, timeouts y presupuestos de ejecución.

- **Acceso excesivo a infraestructura:** el MCP server deberá aplicar autorización y principio de mínimo privilegio. Inicialmente las
herramientas de investigación deberían ser predominantemente de lectura.

- **Acoplamiento al contrato MCP:** una vez que múltiples consumidores dependan de una herramienta, cambios en su schema pueden requerir versionado y compatibilidad hacia atrás.

- **Complejidad prematura:** no todas las capacidades necesitan convertirse en herramientas MCP. Se deberá evitar utilizar MCP únicamente por razones de uniformidad cuando una herramienta local sea suficiente.

- **Observabilidad insuficiente:** la frontera Agent → MCP → sistema externo debe generar información suficiente para reconstruir qué herramienta fue ejecutada, con qué parámetros, cuándo, y cuál fue su resultado.
